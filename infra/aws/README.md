# One-time AWS control-plane setup

`render.py` produces a reusable, project-scoped application permission profile. It does not contact AWS, apply IAM changes, provision an application, select an app topology, or grant every AWS service. An administrator reviews and installs the policies once. Application tasks then use the role-only runtime with a new project UUID; they do not need unrestricted IAM access or a new administrator approval for each bounded execution role.

The initial profile supports Lambda (including URLs, versions, aliases and invocation permissions), DynamoDB, S3 general-purpose buckets/objects, SQS, SNS topics, Secrets Manager and CloudWatch Logs across commercial regions. Other services require a reviewed profile extension using that service's actual resource and condition-key support. CloudFormation, ECS and other delegated execution holds already in the supplied boundary remain in force. Terraform or a trusted SDK can use the same allowed APIs through `factory-aws --exec`; there is no separate administrator credential fallback.

## Private inputs and output

Capture the current runner's DNS identity policy, permissions boundary, trust document and bootstrap-user identity policy with an independently authorized setup identity. Extract the policy documents from AWS response envelopes. Keep the original snapshots and hashes as rollback evidence. Never commit live account IDs, policy ARNs, DNS names, inventories, credentials or rendered policies.

The private configuration has these fields: `account_id`, `runner_role`, `bootstrap_user`, `app_boundary_name`, `app_policy_name`. Dedicated policy names must start with `EngineeringFactory`; the application boundary and data policy names must differ.

```bash
python3 infra/aws/render.py \
  --config "$PRIVATE/config.json" \
  --baseline "$PRIVATE/current-dns-policy.json" \
  --boundary "$PRIVATE/current-boundary.json" \
  --bootstrap "$PRIVATE/current-bootstrap-policy.json" \
  --trust "$PRIVATE/current-runner-trust.json" \
  --output "$PRIVATE/proposed"
```

`PRIVATE` is a previously created mode-700 directory. The output directory must not already exist. Output is mode 700 with mode-600 documents. Rendering refuses an unexpected account/IAM guard, bootstrap target or runner trust source. The renderer deliberately targets the initial bootstrap/DNS baseline; rerender from those retained originals, not an already modified live boundary.

## Enforced scope

- The existing DNS identity policy is copied unchanged. The runner boundary retains the supplied DNS, account, expiry, transport and delegation denials. No core records are adopted, edited or deleted.
- The bootstrap user still has no direct service access and can assume only the exact runner. Project sessions add exactly `factory:managed-by`, `factory:project-id` and `factory:environment`. The runtime requires a canonical nonzero UUID. Application grants also require a UUID-shaped principal project tag, so an untagged session inheriting the runner's control-plane tags cannot perform app writes. The bootstrap policy also rejects ARN wildcard/path metacharacters in project IDs, independently of the runtime. No transitive tags or role chaining are granted.
- Application names start `factory-<project UUID>-<environment>-`. S3 buckets start `factory-<project UUID>-<environment>-`; AWS's bucket and function name limits favor short environment names and resource suffixes. Existing S3/data operations also require the exact configured resource account. Account and region ARN segments cannot come from session input. All 13 canonical provenance tags are required on creation of supported tagged resources. Existing-resource operations require matching project, environment and manager tags where supported.
- S3 uses the UUID/environment bucket namespace during bootstrap: current S3 bucket tags require ABAC enablement before `ResourceTag` conditions become effective. Enable bucket ABAC after tagged creation and retain the private original-provenance inventory; the policy does not claim immutable S3 tags while ABAC is disabled. Object keys and log streams are untaggable children constrained by their parent namespace. Precreate and tag Lambda log groups; application execution roles cannot create untagged log groups.
- Application execution roles live only under `/factory/<project UUID>/<environment>/`. Creation requires the fixed application boundary and provenance tags. Only the fixed data policy can be attached/detached. `PassRole` permits only that project path and Lambda. No role trust editing, arbitrary inline policies, policy creation, boundary removal, service-linked roles, runner modification or account administration is granted. Creating a role's trust is still a consequential action: use the explicit Lambda service principal, never user/account-wide trust.
- The application execution boundary and policy allow project-scoped data operations and log writes, with no infrastructure provisioning, IAM, DNS, account administration or role assumption. Application-role provenance becomes its permanent principal tags. Every data/log Allow is bound to the immutable role PrincipalArn under that exact project/environment path. Its own boundary independently denies ARN metacharacters in both project and environment tags. Overriding a session tag to another valid UUID/environment cannot redirect access to that project's data, even if an incorrectly created trust document permitted TagSession. The central runner retains its existing expiry; application runtime roles remain usable for their deployed app until revoked.
- Changes to original creation tags are denied where resource tags are available; latest run/commit/expiry tags can be updated on owned resources. The private append-only inventory remains authoritative for original provenance and untaggable/provider-limited resources. Provider tagging support varies; a successful simulation alone does not prove a service supplies those context keys.

## Administrator validation and installation

Validate every document with AWS IAM Access Analyzer (`IDENTITY_POLICY`; use `RESOURCE_POLICY` with `AWS::IAM::AssumeRolePolicyDocument` for the trust document). Simulate the complete runner identity-policy set **together with the proposed runner boundary**, and separately the bootstrap and app-execution policy/boundary. Include owned creation/update, missing tags, other project/environment, core ARN, core DNS, expiry/TLS, wrong boundary/policy, PassRole to core/other services, trust changes and boundary removal. The IAM simulator does not correctly evaluate the documented special literal variables `${*}`, `${?}` and `${$}` in the bootstrap and execution-boundary metacharacter guards. Retain that limitation and verify valid and rejected bootstrap project tags using actual STS requests and verify app-role API access with valid and overridden tags after administrator installation; do not report those cases as simulated passes.

Before applying, re-read and compare the live policies/trust with the captured originals and check policy attachment quotas. Create the two dedicated app-execution managed policies and the numbered `runner-app-*` managed policies. Use the intended full provenance for these factory control-plane resources too. Install the complete runner policy set, including explicit deny statements, without exposing a partial allow-only configuration: first install the new boundary and deny-bearing policies, then the remaining grants. Keep the copied DNS baseline unchanged. Finally update the bootstrap identity policy and runner trust to enable the narrowly constrained session tags. These are administrator actions; the factory runtime must never perform its own access expansion.

Read back and hash-check every installed policy and default boundary version. Verify real role assumption with project tags, then test permitted APIs only against disposable, newly created resources recorded in the private inventory. Never probe denial by mutating core assets. Rollback uses the previous boundary default version, original bootstrap policy/trust and removal of only the new policy attachments; preserve evidence and do not delete application data as automatic rollback.

The initial source is validated against the official [AWS service authorization reference](https://docs.aws.amazon.com/service-authorization/latest/reference/service-reference.html), [Lambda ABAC guidance](https://docs.aws.amazon.com/lambda/latest/dg/attribute-based-access-control-example.html), [S3 creation-time tags](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-create-tag.html), and [IAM policy variables](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_variables.html). This is a versioned permission profile, not a claim that ABAC safely supports every AWS service.
