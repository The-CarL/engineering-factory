# Credential and environment readiness gate

**No credentials, Cloud environment, live repositories or deployments are created by this checklist.** Select identities for the environment or app's required capabilities. Proceed only when concrete private targets, effective permissions and operations are approved. The [access matrix](access-matrix.md) is the proposed boundary, not a configured control.

## Decisions to record privately before issuance

| Provider | Required decisions/config names | Scope and proof |
|---|---|---|
| GitHub | `FACTORY_GITHUB_OWNER`; user-backed identity; existing app repositories supplied/manually created by Carlo; private default | Exclude core/factory-control writes; creation/deletion permission not required; verify access, clone, push, PR and CI on the exact supplied repository. |
| Vercel | `FACTORY_VERCEL_TEAM_ID`, `FACTORY_VERCEL_TEAM_SLUG`; existing project or approved provisioning target; app-specific `VERCEL_PROJECT_ID` | Project token for an existing app where supported; team token only when every reachable project is approved. Verify expiry, roles, plan/cost and preview limits. |
| AWS | `FACTORY_AWS_ACCOUNT_ID`, `FACTORY_AWS_REGION`, `FACTORY_AWS_ROLE_NAME`; approved services/actions/resources; protected core inventory | Dedicated factory role(s) in the existing account; approved general service grant, protected inventory, project IAM envelope and fixed boundary; effective-policy simulation and disposable scope tests. |

For each identity record owner, purpose, exact effective actions/resources, expiry, injection/environment scope, revocation/rotation, cost limits and redacted evidence. Record actual excess access and remaining core exposure in the private [exception register](../standards/security.md#access-exceptions); intended boundaries must not be reported as already enforced. Do not substitute broad personal access when an operation fails. No new GitHub organization, Vercel team/subscription, IAM policy or credential is authorized by this checklist.

GitHub repository deletion and file deletion are different permissions: omitting `delete_repo` on a classic token or `Administration: write` on a fine-grained runtime token does not stop content writes. Exclude core repositories entirely from runtime write scope. Carlo creates repositories manually; do not request repository-creation permission as a factory gate. Verify ongoing access after he supplies the repository URL. Selected repositories are not a name-prefix filter. Current scripts require user-backed `GET /user` and organization membership inventory; App installation tokens need a reviewed adapter. See the [provider-specific decisions](access-matrix.md).

Before AWS issuance, approve the general application permission profile from the private protected inventory; account isolation is not available. Review resource-level/tag support, indirect execution and role-passing escalation paths. The runtime must not modify its own trust/policies/boundary, core assets or account controls; app/provisioner IAM stays inside the fixed project-bound envelope. An identity read cannot prove these restrictions.

Before any provider writes, create the private stable project record and provenance inventory described in [the provenance standard](../standards/provenance.md). Verify every deployment path supports metadata or an explicitly reviewed equivalent mapping. Credentials must not grant the ability to claim existing/core assets through retagging.

## Add values outside Git

- Enter secret values directly into the approved Codex vault/environment controls; never into chat, PRs, or `.env.example`. Non-secret target config is also private deployment metadata; keep actual IDs out of this public foundation.
- `GH_TOKEN` and `VERCEL_TOKEN` name CLI environment mechanisms; they do not guarantee compatibility with an injected network-secret placeholder. Verify the pinned tool with the actual transport, client validation and required CLI/API path. Never broaden provider scope or automatically change credential exposure as a retry. Do not `gh auth login --with-token` or persist token files unless that storage is explicitly approved.
- For the **CLI-capable factory**, the preferred Vercel design is a direct secret environment binding named `VERCEL_TOKEN`, personal visibility **Only me**, limited to the selected environment. Approved task code/processes can read its raw token. Changing from a network secret therefore requires explicit approval of that material exposure, independent of provider scope; do not apply this binding merely because these docs changed. Enter values in the personal controls, never chat/source/argv, and never use `--token` with a secret value.
- A REST-only Vercel capability may instead use a personal network-secret `VERCEL_TOKEN` restricted to `api.vercel.com`; do not configure competing bindings for the key. The fixed REST helper still uses HTTPS and refuses redirects under either transport. Record native pinned CLI identity/target results separately: successful REST reads, an API fallback or a shim cannot certify native CLI readiness. See [the names-only design](../runtime/environment.example.json) and [transport gates](provider-workflows.md#vercel-read-only-transport-gates).
- For AWS, use an approved short-lived role/session flow with an intended assume-only bootstrap; verify effective bootstrap and runtime policies separately. Follow [session discipline](../standards/runtime.md#aws-sessions) for exact role/account/region/session checks, short requested lifetime, memory/child-environment credentials and no disk/argv secrets or broad fallback. A requested 900 seconds is not an enforced provider maximum. `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` are possible session variable names, not an instruction to create a long-lived IAM key. Cloud OIDC connections are Enterprise by-request; verify availability first. Locally signed API requests require real compatibility testing with the chosen secret mechanism.
- Cloud environment variables are readable by task processes. Domain-scoped network secrets substitute over HTTPS 443 without a raw process/file value; they are useful only where the CLI/request supports that flow. Personal-vault credentials must be scoped to the selected environment. [Official configuration guide](https://learn.chatgpt.com/docs/environments/cloud-environments#configure-environment-variables-and-network-secrets).
- Set approved network domains and egress policy for package/tool installation, GitHub clones/API, Vercel API/build flows, and AWS endpoints only as needed. Test support; do not assume arbitrary network access or that a connector grants CLI access.

## Environment capability acceptance

Complete applicable gates with their actual dependencies; this does not prescribe a sequence or topology for every application.

1. Review/merge the foundation with required checks passing, then approve applicable access/provenance design and private targets for selected provider capabilities.
2. Decide the selected identities and provisioning versus ongoing scope, including GitHub owner, Vercel project/team or AWS bounded role when relevant. Approve expiry, cost limits and exact capability checks; issue/inject only reviewed credentials. Do not widen permissions to satisfy a script.
3. Prepare/reconcile the factory-linked Cloud environment from reviewed versioned runtime source. Verify required pinned tools, real CLI contracts, network and each selected credential transport. Save, then observe the existing publish job to confirmed completion; preserve the last confirmed release and do not duplicate unknown operations. [Setup entry points](setup.md#codex-cloud-gate-not-performed-by-foundation-setup).
4. Start a fresh task on the intended published revision; verify retained-file integrity, dependencies and startup, then provider identity/target preflight. Record native CLI and API results independently in the private release manifest. Validate effective scopes separately using non-destructive simulation where available and authorized disposable allowed/denied tests; never attempt destructive operations on core assets.
5. Use [phone/continuation capability evidence](mobile-workflow.md#capability-and-recovery-evidence) where claimed, with representative authorized operations. Keep application acceptance workload-specific. Record exact identities, source/run metadata and relevant operational results privately.
6. Where app CI/CD is configured, use native integration or narrowly trusted app-owned authentication. Verify provenance on the actual deployment path; do not copy factory credentials into apps.
7. For selected AWS capabilities, review the workload IaC plan, private state, cost, provenance, rollback/retry and cleanup before execution. Include these and any DNS operations explicitly in approved scope; an initial authorization can cover them together.

Track each gate independently in private evidence. A saved environment, read-only success or one working provider does not establish publication, another CLI/transport, effective write/denial boundaries, cross-repo execution, mobile continuation or deployment. Do not promote an untested or pending gate to complete.
