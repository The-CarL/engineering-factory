# Phone operation and fresh-task continuation

Use the reusable factory environment to go from an idea through collaborative design and a prototype to a verified working solution and agreed hosting. Start or continue from a phone using voice or text where supported by the selected client; verify any claimed input modality. [Project guidance](new-project.md) and [conversational delivery](../standards/conversational-delivery.md) describe how the agent leads the work. Phone operation does not prescribe an app type or provider.

## Starting or continuing work

Select the intended environment and describe the desired outcome or existing app. The agent can derive a suitable new private repository target from authorized scope and known configuration, or ask when the target is consequentially unresolved. Reuse known private configuration and exact authorization; prepare missing consequential scope together under [bounded project work](../standards/bounded-runs.md). Keep normal decisions and routine authorized operations moving without repeated prompts. Another chat is optional and needs human authority for its recipient/purpose.

Lead codesign, establish observable success and resolve unknowns by asking, inferring or postponing with a trigger. Check actual source/runtime revisions and the intended build/test/hosting/data path early. Surface blockers with a concrete next action before substantial dependent implementation, continue unaffected work and keep the user informed without waiting for a status request.

The agent verifies the target repository/origin and applicable instructions, then uses the capabilities needed for the request. Seed new local agent/engineering instructions when appropriate; integrate differing instructions deliberately. Implement product-specific commands, relevant checks and app-owned CI/hosting operations. Record actual results, source/configuration identity and private provenance/inventory.

Verification follows the workload. Use a browser when UI behavior matters, requests for service interfaces, and execution/output checks for jobs or other runtimes. Use the actual mechanism available in the task; local Chrome configuration alone does not establish Cloud browser capability. Preserve selected provider protections and permission boundaries.

## Fresh-task continuation

A new task may have a fresh VM/actor. Make source and needed private recovery artifacts durable through approved Git push/export and verify restoration before relying on them. A summary or workspace-local hash does not transfer source bytes.

Use the same factory environment, clone the saved app identity with `clone-repo.sh`, and verify origin/visibility. Read its AGENTS/CLAUDE/ENGINEERING instructions and actual commands. Restore approved private configuration through the established mechanism, reconcile existing resources/operations and preserve project identity/original provenance before changing the app. Keep factory execution credentials out of app source/CI.

## Conversational delivery acceptance

Use actual sessions and keep redacted evidence privately. These scenarios test the user experience as well as selected environment capabilities; local helper tests alone cannot pass them. Choose a representative brief with a meaningful unresolved question and a decision that can wait, so asking, inferring and postponing are exercised without forcing unnecessary questions into every task. Select apps and providers from their needs.

| Scenario | Required observed behavior and evidence |
|---|---|
| Idea to agreed design | Start with a short product idea rather than a complete engineering specification. The agent proposes an approach and observable acceptance, asks about a consequential unknown before dependent work, states a reasonable inferred detail, and records a decision that can wait with its reopening trigger. The user can respond conversationally without completing a universal form. |
| Prototype to working solution | Within resolved scope, create the independent remote repo, implement a usable prototype, incorporate feedback, run meaningful checks and complete agreed hosting. Verify the real requested behavior and integration/data durability where relevant. Record exact source, operation/deployment evidence and acceptance results. A local repo or mock is not proof of a remote repo or hosted solution. |
| Early capability blocker | Use a known unavailable required capability or a controlled local fixture; do not revoke live credentials or mutate core assets to induce failure. The agent identifies it before substantial dependent work, distinguishes missing capability from missing intent, explains the affected outcome and concrete fix/input needed, and continues safe independent work. This can verify blocker handling while the blocked delivery capability remains unaccepted. |
| Bounded access failure and truthful status | Use a controlled connection failure or pending-approval fixture. The agent reports the first failure and the affected milestone, separates the observed error from unverified permission hypotheses, stays within its stated diagnostic budget and gives updates within a minute while active. No unchanged retry loop occurs. Remote creation, push and deployment claims each require their corresponding readback; local initialization and instruction seeds remain labeled preparation. Do not alter live credentials or provider permissions for this scenario. |
| Feedback, status and deferred decisions | During work, provide a correction and request status. The agent answers promptly, preserves the overall objective and existing answers, updates the design/state, and resumes. When a postponed decision's trigger is reached, the agent resolves it before its dependent action. Pending tool approvals and partial verification are visible without repeated status requests. |
| Stop, explain and restart | Ask about execution concerns; the agent answers directly before more tools. Then explicitly stop the task: no new task actions occur, supported cancellation is honored and unknown external outcomes stay recorded. Ask for a separate factory change; the earlier app stays stopped. Only an explicit restart permits resuming it, with state reconciliation before further mutations. |
| Fresh-session continuation | Start another task in the same intended environment with restored durable source/private records. Verify actual checkout/runtime revisions and loaded instructions, reconcile resources and continue from the saved goal, decisions, scope and next actions without repeating resolved questions, losing user work or duplicating resources. |

Record each scenario as verified, blocked or not run, with source/runtime revision, the relevant decision exchange, actual actions/results and remaining gaps. The delivery claim requires a completed representative idea-to-hosted-solution flow and fresh-session continuation; correct blocker reporting does not establish deployment capability. Helper, transport, permission, application and session-behavior evidence remain distinct. These documents do not claim the live scenarios have passed.

## Capability and recovery evidence

Factory release acceptance records only the capabilities claimed for that release. Use representative authorized operations for repository access, selected hosting, phone interaction or continuation; a project's acceptance can use a different workload and relevant checks. Where fresh-task continuation or retry safety is claimed, demonstrate it without duplicate resources, changed origins or lost user files.

For unknown provider outcomes, reconcile intent, exact IDs/source/provenance and state before any further mutation. Repository retry evidence does not establish deployment retry behavior. Restore durable source in a fresh location, verify commit/history as required and run relevant app commands. Record cleanup ownership/expiry, costs and remaining blockers privately; cleanup requires its approved scope. Keep provider IDs, raw diagnostics and credentials out of the public factory.
