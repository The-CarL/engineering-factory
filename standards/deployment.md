# Reproducible deployment

- Each app owns relevant validation/release commands and any CI/CD. Use reviewed provider-native integration or narrowly trusted app-owned authentication where supported. Never copy factory execution credentials into app repositories or CI.
- Apply [project ownership and provenance](provenance.md) to all deployment paths. Record pinned runtime/tool versions, lockfiles, artifact/source commit, stable project/environment identity, creation and latest run/actor attribution. Preserve original creation history in private inventory; do not globally retag unrelated resources on every run.
- Distinguish pinned local client tools from provider-controlled build tools; verify the actual remote engine/package-manager/install contract and retain observed versions. A build configuration error does not imply a permission failure.
- Run checks before deployment. Verify authenticated identity, team/account/region, and exact resolved project immediately before action. For Vercel, use the intended app directory and `vercel project inspect --non-interactive`; stop on missing/mismatched context rather than auto-linking.
- Establish the private project record before writes. For Vercel CLI/API, supply required deployment metadata and verify it through provider readback. For native Git/redeployment flows, verify a supported metadata mechanism or explicitly reviewed equivalent mapping before enabling the path. Never assume CLI metadata is inherited by Git integration.
- Check first-deployment behavior before a preview request: Vercel can assign the first deployment to production. Block preview-only writes without a verified READY production baseline; an initial production-classified release needs explicit scope in the initial plan or approval of the prepared change. Use the [provider workflow contracts](../docs/provider-workflows.md) for the narrow REST path, source-byte verification and operation journal.
- Use an appropriate authorized isolated environment for non-production work. Production promotion requires explicit scope and rollback/operational criteria. Enumerate deployment and custom-domain/DNS operations separately; initial authorization may cover them together. Prepare approval only for excluded operations or newly required changes. Resource scope alone does not make a credential deployment-only.
- Verify actual workload behavior in the intended runtime: relevant rendering, request/response, job execution/output or component integration, plus source/configuration identity and exact private resource inventory/provenance. A successful CLI exit is insufficient. Missing resource/run attribution fails acceptance.
- Keep a rollback reference and verify provider-specific rollback semantics, data compatibility, and retained artifacts. Plan migration/restore before irreversible data changes.
- Retry using known repository/project/deployment identities. Inspect unknown outcomes; reconcile child resources and private append-only operation events before retrying. Do not create duplicate projects, overwrite original attribution, or redeploy blindly. Record a concise redacted result and cleanup responsibility.

## Execution environment releases

Apply [runtime acceptance](runtime.md#release-evidence-and-recovery) to environment build artifacts as well as app releases. Link reviewed setup/wrapper source, private configuration revision, tool versions and retained-file hashes to the observed environment/snapshot or publish job. Save, publish and fresh-task readiness are distinct gates. Preserve the last confirmed release; reconcile an existing job or unknown outcome before retrying. Separate provider API/CLI/read results from remaining write, denied-behavior, deployment and phone-continuation proof. Never report a queued, stale or failed publish as complete.
