# Infrastructure and cost

- Use exact approved provider targets. For this factory's AWS Phase 3 design, use dedicated bounded factory role(s) in the existing AWS account; existing/core assets remain outside mutation scope. Vercel isolation depends on approved team/project token scopes. See the [access matrix](../docs/access-matrix.md); no provider policy is configured by these standards.
- Define reproducible infrastructure as code when appropriate; choose Terraform, CDK, CloudFormation, or the target repo's established tool. Pin provider/plugin/tool versions and lockfiles. Never commit live state or variable secrets.
- Before apply, review the exact target, plan/diff, resource count, estimated recurring and one-time cost, public exposure, allowed services, rollback, and cleanup owner. Planning can read remote APIs; it is not universally offline or a permission check.
- Enforce the approved permission profile, project namespaces, protected-resource exclusions and policy boundaries/session constraints. A general cross-service profile can support new services without individual enablement; verify actual resource-level IAM and tag support for each workload. A namespace, tag or universal `Delete*` deny cannot protect all existing infrastructure.
- Keep runner/bootstrap/admin identities and central policies outside app authority. Permit application/provisioner IAM only through the reviewed project-path envelope, fixed non-removable boundary and bounded PassRole invariant; verify existing role boundaries before activation. Scope indirect CloudFormation/other deployment execution too; account-level IAM, organization, billing, security, shared DNS/network, cross-account and core-resource mutations require separate authorization.
- Apply the mandatory [project ownership and provenance standard](provenance.md) to every resource, child resource and deployment: stable project/environment identity, source/run/actor attribution, tag-on-create where supported, reviewed untaggable exceptions and private inventory/readback. Prevent retagging core assets to claim ownership and protect original creation attribution. Do not adopt existing assets implicitly.
- Set a user-approved budget/alert recipient and usage limits before billable tests. Budget alerts often notify after usage rather than prevent it; use service quotas and provider-enforced limits as well. Do not create a budget subscription or email alert without authorization.
- Validate effective permissions through non-destructive simulation and authorized disposable positive/negative tests. Do not test denied changes against core assets. Identity preflight alone does not validate the boundary.
- Track exact resource IDs privately, ownership, cost/expiry/cleanup and restore procedures. Preserve historical operation records. Never auto-destroy resources after an ambiguous failed apply; reconcile state with the approved plan first.
